Intro                                                               *pesto-intro*

`pesto.nvim` is a Bazel runner plugin for Neovim. It integrates with Bazel
through the Build Event Protocol to support things like loading compilation
errors into the quickfix list.
                                                                    *pesto-types*
Note: Throughout this manual there are references to LuaLS types defined in
Pesto's source code (e.g., `pesto.Config`).

================================================================================
Configuration                                                      *pesto-config*

You don't need to call a `setup` function to configure `pesto.nvim`. You can
instead just set `vim.g.pesto`. Here is the default configuration:

>lua
    ---@type pesto.Config
    vim.g.pesto = {
        --- Name of bazel binary that Pesto invokes. Should be on your `$PATH` or a
        --- path to an executable.
        bazel_executable = "bazel",
        -- Callback invoked to run bazel.
        bazel_runner = function(opts)
            require("pesto.components").default_runner(opts)
        end,
        --- Map from a "target resolver ID" to a method that returns a Bazel
        --- target resolver.
        build_target_resolvers = require("pesto.config").DEFAULT_TARGET_RESOLVERS,
        --- Logging level (see `:checkhealth pesto` to get the log file's path)
        log_level = "info",
        --- Indicates which logs Pesto should use to populate the quickfix window
        --- following a build.
        quickfix_log_source = "bep",
        --- When set to true, Pesto will inject the `--build_event_json_file=$BEP_FILE`
        --- Bazel command line option. If you use the default runner, then following
        --- the build Pesto will parse the resulting build events tree and the quickfix
        --- list.
        enable_bep_integration = true,
        --- When this option is true and when you are using the default runner, a
        --- terminal buffer will be opened automatically when bazel is invoked.
        auto_open_build_term = true,
        --- This list is used to determine the errorformat string to use to parse the
        --- output of a failed action. It effectively defines a mapping from Bazel
        --- action mnemonics to errorformats.
        errorformats = {},
        --- The default set of errorformats. Covers some of the major rule
        --- sets. You shouldn't need to override this.
        default_errorformats = {
          ...
        }
        --- Configuration for the `:Pesto bazel` subcommand auto-completion
        cli_completion = {
            --- Completion strategy. There are three modes:
            --- * "bash": With this mode completion gets powered by the Bazel's own bash completion script (e.g., /etc/bash_completion.d/bazel)
            --- * "lua": A less sophisticated lua implementation of Bazel
            --- * "automatic": With this mode, we attempt to first use the bash completion script. If it's unavailable, then we fallback to the lua implementation.
            mode = "automatic",
            --- For the "bash" completion strategy, this is the amount of time to wait
            --- for the bash completion script to finish before timing out.
            bash_timeout = 15000,
            --- Absolute path to the bash completion script. If the setting is not defined,
            --- then Pesto falls back to searching for the script in `/etc/bash_completion.d/`
            bash_completion_script = nil,
        },
    }
<

If you prefer, however, `pesto.nvim` does support a setup function:

>lua
    ---@type pesto.Config
    local config = {...}
    require("pesto").setup(config)
<

--------------------------------------------------------------------------------
Config fields                                                *pesto.config.fields*

`bazel_executable`                                   *pesto.config.bazel_executable*
    type: `string`
    default: `"bazel"`

    Name of bazel binary that Pesto invokes. Should be on your `$PATH` or a path
    to an executable.

`bazel_runner`                                         *pesto.config.bazel_runner*
    type: pesto.RunBazelFn
    default: Pesto's default runner (see |pesto-config|).

    Pesto calls this callback to invoke bazel. By default Pesto uses its own
    default runner callback (see |pesto-default-runner|).

`build_target_resolvers`                     *pesto.config.build_target_resolvers*
    type: {
      [string]: fun(context: pesto.RunBazelContext): {query: string}|{targets : string[]}
    }
    default: require("pesto.config").DEFAULT_TARGET_RESOLVERS

    This option is used by Pesto's `build` subcommand (|pesto-commands-build|).
    The option defines a mapping from a string ID to a function that returns
    either a target query or targets. The `build` subcommand will use the result
    to invoke a build with the given targets.

    The function takes a `pesto.RunBazelContext` which has the following
    definition:
>lua
    ---@class pesto.RunBazelContext
    ---@field workspace_dir string
    ---@field package_dir string|nil
    ---@field package_label string|nil
    ---@field buf_nr number
<
    This context should be used to dynamically create the list of targets or
    the query needed to invoke the build.

    When a query is returned, Pesto will run the query and then invoke a build
    using the returned targets. When a targets are returned, Pesto runs the
    build directly using the given targets.

    As an example, here are the default resolvers
    (`require("pesto.config").DEFAULT_TARGET_RESOLVERS`):

>lua
    ---@type pesto.TargetResolvers
    local DEFAULT_TARGET_RESOLVERS = {
      ['all'] = function(context)
        return {
          targets = { string.format('%s:all', context.package_label) },
        }
      end,
      ['tests'] = function(context)
        return {
          query = string.format('tests(%s:*)', context.package_label),
        }
      end,
    }
<
    Tip: It's possible you'll want different resolvers based on the file type
    of the source file you're editing. You can detect the file type based on
    the context's `pesto.RunBazelContext.bufnr` field. Another option is to use
    an autocommand or filetype plugin to set `build_target_resolvers` at the
    buffer level. Pesto merges buffer-level options with the global-level
    options, giving priority to the buffer level.

`enable_bep_integration`                     *pesto.config.enable_bep_integration*
    type: `boolean`
    default: `true`

    This option enables the default runner's (|pesto-default-runner|) BEP
    integration (|pesto-bep-integration|).

`quickfix_log_source`                           *pesto.config.quickfix_log_source*
    type: `"bep"|"pty_output"`
    default: `"bep"`

    This option indicates which logs Pesto should use to populate the quickfix
    window following a build.

    There are two options:
    * `"bep"`: Pesto will find and fetch failed action logs using the log file
    paths found in BEP logs.
    * `"pty_output"`: Pesto will do its best to parse the bazel command's output
    sent to the Neovim pseudo terminal.

    Note: When `quickfix_log_source` is set to `"bep"` the
    `enable_bep_integration` option (|pesto.config.enable_bep_integration|)
    is always taken to be true.

    Pesto defaults to using the `"bep"` option. This is because failed action
    logs are cleaner compared to the commands bazel command's progress logs.
    For example, here's the failed action logs for Java compilation error:

>bash
    src/main/java/net/starlark/java/syntax/LambdaExpression.java:43: error: cannot find symbol
      public xpression getBody() {
             ^
      symbol:   class xpression
      location: class LambdaExpression
<

    Compare those logs with bazel command's raw output:

>bash
    INFO: Analyzed target //src/main/java/net/starlark/java/syntax:syntax (0 packages loaded, 0 targets configured).
    ERROR: /home/user/dev/bazel/src/main/java/net/starlark/java/syntax/BUILD:17:13: Building src/main/java/net/starlark/java/syntax/libsyntax.
    jar (42 source files) and running annotation processors (AutoAnnotationProcessor, AutoBuilderProcessor, AutoOneOfProcessor, AutoValuePro
    cessor, AutoValueGsonAdapterFactoryProcessor) failed: (Exit 1): java failed: error executing Javac command (from target //src/main/java/
    net/starlark/java/syntax:syntax) external/rules_java++toolchains+remotejdk21_linux/bin/java '--add-exports=jdk.compiler/com.sun.tools.ja
    vac.api=ALL-UNNAMED' '--add-exports=jdk.compiler/com.sun.tools.javac.main=ALL-UNNAMED' ... (remaining 19 arguments skipped)
    src/main/java/net/starlark/java/syntax/LambdaExpression.java:43: error: cannot find symbol
      public xpression getBody() {
             ^
      symbol:   class xpression
      location: class LambdaExpression
    Target //src/main/java/net/starlark/java/syntax:syntax failed to build
    Use --verbose_failures to see the command lines of failed build steps.
    INFO: Elapsed time: 1.008s, Critical Path: 0.75s
    INFO: 2 processes: 2 internal.
    ERROR: Build did NOT complete successfully
    INFO: Build Event Protocol files produced successfully.

    [Process exited 1]
<
    Notice how the compilation error is embedded among various other unrelated
    status logs.

    When `quickfix_log_source` is set to `pty_output`, Pesto does its best to
    tease out individual action logs, but there may be cases where it gets it
    wrong. If you encounter such cases, please log an issue.

    For a deeper discussion of Pesto's BEP integration please see
    |pesto-bazel-concepts|.

    One reason to consider `pty_output` over `bep` is if remote caching is
    involved. Please see |pesto-remote-caching| for more information.

`auto_open_build_term`
    type: `boolean`
    default: `true`

    When this option is set to true, the default runner will automatically open
    the build terminal used to invoke Bazel.

    Regardless of whether or not the default runner opens, Pesto will always
    send a notification for the build result.

`errorformats`                                         *pesto.config.errorformats*
    type: `pesto.ActionErrorformat[]`
    default: {}

    This option defines a mapping from a Bazel action mnemonic to an
    |errorformat|. This mapping is used by Pesto to load the quickfix list
    following a failed build.

    If you're a new or casual Bazel user "rule kind" and "action mnemonic" may
    be new terms. Please see |pesto-bazel-concepts| for a deeper explanation.

    To understand this setting it's also helpful to look a the
    `pesto.RuleActionErrorformats` type definition along with its supporting
    type `pesto.ActionErrorformat`:

>lua
    ---@class pesto.RuleActionErrorformats
    ---@field rule_kind string A lua string pattern
    ---@field action_errorformats pesto.ActionErrorformat[]

    --- Maps a rule's actions' mnemonics to either a errorformat string or compiler
    --- plugin (which should in turn define a errorformat)
    ---@class pesto.ActionErrorformat
    ---
    --- A lua string pattern
    ---@field action_mnemonic string
    ---
    --- The compiler plugin that should define the errorformat to use for parsing
    --- the action's stderr output.
    ---@field compiler string|nil
    ---
    --- Errorformat string (:help errorformat)
    ---@field errorformat string|nil
    ---
    --- Some compilers produce output with syntax highlighting using ANSI escape
    --- codes. When `strip_escape_codes` is set to true, Pesto will strip out the
    --- escape codes before parsing the errors for the quickfix window.
    ---@field strip_escape_codes boolean|nil
<

    Finally, let's look at a snippet that shows the value of Pesto's default
    errorformats, as defined in `lua/pesto/config.lua`
    (|pesto.config.default_errorformats|):

>lua
  {
    -- rules_cc
    {
      action_mnemonic = 'CppCompile',
      compiler = 'gcc',
    },
    -- rules_go
    {
      action_mnemonic = 'GoCompilePkg',
      compiler = 'go',
    },
    -- rules_java
    {
      action_mnemonic = 'Javac',
      compiler = 'javac',
    },
    {
      action_mnemonic = 'Turbine',
      errorformat = "%f:%l: %m"
    },
    -- rules_rust
    {
      action_mnemonic = 'Rustc',
      compiler = 'rustc',
      strip_escape_codes = true,
    },
    -- rules_scala
    {
      action_mnemonic = 'Scalac',
      errorformat = table.concat({
        -- Scala 2 pattern
        '%f:%l:\\ error:\\ %m',
        -- Scala 3 patterns
        '--\\ [E%n]\\ %m:\\ %f:%l:%c%.%#',
        '--\\ %m:\\ %f:%l:%c%.%#',
      }, ','),
      strip_escape_codes = true,
    },
  }
<

    Let's consider a few examples. First, let's say we build a scala_library
    target. Scala compilation is executed using an action with the mnemonic
    `Scalac`. Now, let's say the test fails. Pesto needs find the errorformat
    to use to parse the error logs.

    The failed action's mnemonic will be `Scalac`, so Pesto will parse the
    error output using this errorformat:

>lua
  {
    action_mnemonic = 'Scalac',
    errorformat = table.concat({
      -- Scala 2 pattern
      '%f:%l:\\ error:\\ %m',
      -- Scala 3 patterns
      '--\\ [E%n]\\ %m:\\ %f:%l:%c%.%#',
      '--\\ %m:\\ %f:%l:%c%.%#',
    }, ','),
    strip_escape_codes = true,
  }
<

    Next let's say we triggered a failing Java build while trying to build a
    Java library. In this case, the target likely came from the rule
    `java_library` that triggered the compilation action with the mnemonic
    `Javac`.

    In this case the relevant config maps `Javac` to is the following value:

>lua
    {
        ...
        compiler = "javac",
    }
<

    Notice that in this case there is no |errorformat| string. Instead the
    config defines the `pesto.ActionErrorFormat.compiler` option. Neovim
    already ships with a number of compiler plugins (see |compiler|), including
    for `javac`. These plugins already define an `errorformat` string. Instead
    of having to copy these over into the Pesto's config Pesto allows you
    specify the compiler plugin to use and will use its errorformat string.

    Neovim doesn't ship with a compiler plugin for Scala, so we had to define
    the errorformat manually.

`default_errorformats`                        *pesto.config.default_errorformats*
    type: `pesto.ActionErrorformat[]`
    default: See `lua/pesto/config.lua`

    This option defines Pesto's default mapping from a Bazel action mnemonic to
    an |errorformat|. This mapping is used by Pesto to load the quickfix list
    following a failed build.

    This option mirrors |pesto.config.errorformats| but comes already
    populated with mappings for some of Bazel's more well-known rule sets
    (e.g., rules_cc, rules_go, rules_java, etc.)

    The full definition is defined in `lua/pesto/config.lua`. You can also
    see a copy of the configuration in the documentation for
    |pesto.config.errorformats|.

`cli_completion`                                     *pesto.config.cli_completion*
    type: `pesto.CliCompletionConfig`
    default: See individual config below

    This setting affects the auto-completion behavior of Pesto's `bazel`
    wrapper command: `:Pesto bazel ...`

    Individual fields are described below.

`cli_completion.mode`                           *pesto.config.cli_completion.mode*
    type: `"lua"|"bash"|"automatic"`
    default: "automatic"

    Pesto provides two completion strategies for its `bazel` subcommand:

    * `"bash"`: With this mode Pesto uses Bazel's native bash completion script
      (e.g., /etc/bash_completion.d/bazel) to generate completions.
    * `"lua"`: With this mode Pesto uses a less sophisticated Lua-based
      implementation. This mode does not support auto-completing Bazel's
      command line options.

    By default the value of `cli_completion.mode` is set to "automatic". This
    means Pesto will first try to use `"bash"` strategy. If the completion
    script cannot be found, then Pesto falls back to the `"lua"` strategy.

    The `"bash"` strategy relies on inter-process communication, which may make
    the `"bash"` strategy appear slightly slower. If your completion needs do
    not require fuller fidelity with the bash CLI experience, you may consider
    using the `"lua"` strategy which is more responsive.

`cli_completion.bash_timeout`           *pesto.config.cli_completion.bash_timeout*
    type: `number`
    default: `15000`

    Defines the maximum number of milliseconds to wait for a bazel completion.
    This setting only applies when using the `"bash"` completion mode
    (|pesto.config.cli_completion.mode|).

                              *pesto.config.cli_completion.bash_completion_script*
`cli_completion.bash_completion_script`
    type: `string|nil`
    default: `nil`

    Absolute path to the bash completion script that Pesto should use for
    completions. This setting only applies when using the `"bash"` completion
    mode
    (|pesto.config.cli_completion.mode|).

    Note: When the value of `bash_completion_script` is the unset Pesto searches
    among a few well known locations. See
    `require('pesto.config').DEFAULT_BASH_COMPLETION_SCRIPTS` for the default
    locations.

`log_level`                                               *pesto.config.log_level*
    type: `"trace"|"debug"|"info"|"warn"|"error"`
    default: "info"

    This option defines the minimum level of logs that are output.

Commands                                                         *pesto-commands*

Pesto's CLI is similar to `git`: There is a single top-level command and
various sub-commands. Here is the format:
>viml
    :Pesto <sub-command>
<
Listed below are the possible sub-commands:

                                                            *pesto-bazel-command*
`bazel <args>`
    The `bazel` sub-command is a thin wrapper around the actual `bazel`
    executable. The `<args>` that you give it are the same ones you'd give when
    invoking `bazel` directly from a shell.

    By default auto-completion for the Pesto `bazel` sub-command is backed by
    Bazel's own bash completion script (e.g., `/etc/bash_completion.d/bazel`).
    You may point Pesto at the completion script to use through the
    |pesto.config.cli_completion.bash_completion_script| setting. If
    the bash completion script is not available, Pesto falls back to a simpler,
    Lua-based auto-completion implementation.

    Auto-completion implicitly uses the current source file's directory as the
    CWD. Say you are editing some file `foo/bar/baz.c` in the package
    `//foo/bar`. You then trigger auto-completion by typing out the following
    at the Neovim command line:
>viml
    :Pesto bazel build :<TAB>
<
    You should get the same target completion options had you triggered
    auto-completion from the `foo/bar` directory in the shell:
>bash
    # Starting from the repo root
    $ cd foo/bar
    $ bazel build :<TAB>
<
    This can be helpful for avoiding typing out the fully qualified targets
    when invoking Bazel.

`build [target-resolver-id]`                                *pesto-build-command*
    `target-resolver-id`: This ID acts as a key into the map defined by the
    |pesto.config.build_target_resolvers| option.

    The `build` command provides a way to quickly invoke a Bazel build. Its
    primary use case is invoking a build for targets that directly depend on
    the source file currently being edited.

`sp-build`                                               *pesto-sp-build-command*
    Opens the BUILD or BUILD.bazel file for the current file's package in a
    horizontal split.

`vs-build`                                               *pesto-vs-build-command*
    Opens the BUILD or BUILD.bazel file for the current file's package in a
    vertical split.

`copy-last-bazel-command`                         *pesto-copy-last-bazel-command*
    Yanks the last run Bazel command to the unnamed ("") and plus registers
    ("+). So assuming the clipboard provider is provided, then the Bazel
    command should be available to paste into an external terminal via the
    system clipboard.

`load-quickfix <bep-json-file>`                             *pesto-load-quickfix*
    `bep-json-file`: Path to a BEP JSON log file

    Loads the quickfix list for the failed actions logged to the given BEP JSON
    file.

    This command can be useful if you're writing your own runner or if you need
    to load errors from a BEP log file that was generated elsewhere (e.g., a
    CI/CD pipeline artifact).

`dump-failed-action-logs [dest-dir]`      *pesto-dump-failed-action-logs-command*
    `dest-dir`: Destination for the log files

    This command is useful for debugging and adding support for additional rule
    sets. See the |pesto-adding-rule-sets| guide for an illustration of its
    usage.

    The command should be invoked following a failed build. It does the
    following things:

    1. Searches the BEP logs for failed actions
    2. Fetches the stderr output for the failed actions it finds
    3. Writes the action logs to files in [dest-dir] if it is given or to some
       temporary directory if [dest-dir] is not given

    Each failed action that has stderr logs to dump will produce a single file
    containing the logs. The name of the file follows this format:

>text
    <action_mnemonic>-<number>
<
    The `<action_mnemonic>` is the mnemonic for the failed action, the
    `<number>` part is not meaningful and is added to ensure uniqueness.

Bazel concepts                                              *pesto-bazel-concepts*

This section gives a quick primer on key Bazel concepts underpinning Pesto.

One of Pesto's key features is its quickfix integration. Here's how it works:

First, we'll assume you're using BEP logs as your quickfix source. In other
words, the |pesto.config.quickfix_log_source| option is set to `"bep"`.

When a Bazel build is executed, it can be configured to emit a log of "build
events". When the BEP integration is enabled (|pesto-bep-integration|), Pesto
configures Bazel to emit these events to a file by automatically injecting the
--build_event_json_file option. After the build finishes, Pesto parses and
processes the events in the log file.

When you trigger a Bazel build you specify one or more build targets. A build
target is defined in BUILD (or BUILD.bazel) files using "rules." For example in
a Java project you'll likely find many BUILD files contain targets defined by
the `java_library` and `java_binary` rules.

When you create a target using a rule, you normally specify the target's
inputs, which is often source files. The rule then defines the steps to take
those inputs and produce outputs, such as a library or executable.

In Bazel terms the steps taken to produce an output are called "actions."
Actions are given short memorable names called "mnemonics." For example, the
Java Bazel rules often involve an action that invokes the Java compiler. This
action is given the mnemonic "Javac".

When an action fails--for example the Java compiler found compilation
errors--Bazel emits a build event for the failed action. Following the build
Pesto finds this failed action event. The failed action includes the actions
mnemonic and a URI pointing to the action's stderr output.

Pesto fetches the failed action's output and then uses the mnemonic as a key to
look up which errorformat it should use to parse the output load into the
quickfix list (|pesto.config.errorformats|)

Note: Pesto does not parse the progress output that Bazel emits during
execution. Pesto's primary source of build information is the build events log.

================================================================================
Default runner                                             *pesto-default-runner*

When Pesto needs to invoke Bazel it calls the callback given by the
|pesto.config.bazel_runner| option. This section describes Pesto's default
runner.

Pesto's default runner runs the Bazel command in a terminal window. If the
|auto_open_build_term| option is set to `true`, then terminal window will
automatically appear showing Bazel's output. Regardless of the
|auto_open_build_term| setting, Pesto will always send a notification when the
Bazel invocation finishes.

================================================================================
Build Events Protocol (BEP) integration                   *pesto-bep-integration*

Pesto is capable of consuming Bazel's build event logs. This integration is
controlled by the |enable_bep_integration| setting, which is set to `true` by
default.

When the BEP integration is enabled, default runner (|pesto-default-runner|)
automatically injects `--build_event_json_file={BEP_FILE}` Bazel option. After
Bazel finishes Pesto does the following things:

    1. Loads the `{BEP_FILE}`
    2. Searches the BEP events for failed actions
    3. Loads the logs associated with the failed actions
    4. If the failed actions have a corresponding `errorformat` mapping, Pesto
    loads the errors into the quickfix list.

For a more detailed explanation see |pesto-bazel-concepts|.

Remote caching (experimental)                              *pesto-remote-caching*

This section explains how Pesto handles quickfix loading under these conditions:

    * |pesto.config.quickfix_log_source| is set to `bep`.
    * You're using Bazel with remote execution or caching.
    * Action logs are stored in the remote cache.

Before getting into Pesto's behavior under these circumstances, consider trying
|pesto.config.quickfix_log_source| with the `pty_output` option first. It may
work well-enough and avoids some of the latency of fetching action logs from
the remote cache discussed below.

More advanced Bazel setups often involve Remote Build Execution (RBE) or remote
caching. When RBE is used Bazel will store action logs in the remote cache.

When action logs are stored remotely, the `{BEP_FILE}` will refer the logs using
a `bytestream` URI like this:
>
    bytestream://rbe.util.acme.org:8980/blobs/477b2a3983637d7633933691800642a388a38e1dd81ebe12304a603dc3b3dfba/226
<
When |pesto.config.quickfix_log_source| is set to `bep` Pesto must fetch
these logs in order to populate the quickfix list.

A `bytestream` URI is served by a gRPC endpoint. Since implementing a gRPC
client in Lua would be a significant undertaking, Pesto delegates the remote
log fetches to an external ByteStream gRPC client.

The ByteStream client Pesto uses is written in Python. You can find it in the
`tools/pesto-remote-apis-helpers` directory.

Pesto does the following when it detects logs are stored remotely at some
ByteStream URI:

  1. Checks to see if the helper Python script is set up; the script
  has a few dependencies (see
  `tools/pesto-remote-apis-helpers/pyproject.toml`)
  2. If the `tools/pesto-remote-apis-helpers` script has been set up, Pesto
  uses it to fetch the logs; otherwise, Pesto prompts you to install the
  script using the |install-remote-apis-helpers| command.

One disadvantage of loading the quickfix list using the remotely stored
compiler logs is the latency. This is where using `pty_output` for
|pesto.config.quickfix_log_source| may be more practical; Bazel's progress
output is immediately available.
